# SalonPro Backend

Backend REST de SalonPro, desarrollado con Java 21, Spring Boot y PostgreSQL.

## Tecnologías

- Java 21
- Spring Boot
- Spring Web
- Spring Data JPA
- Hibernate
- Jakarta Validation
- PostgreSQL
- Maven
- springdoc-openapi (Swagger UI)

## Arquitectura del backend

```
Controller
    → Port IN
    → Application Service
    → Domain
    → Port OUT
    → Persistence Adapter
    → Spring Data JPA
    → PostgreSQL
```

Cada módulo de negocio (por ejemplo, `usuario` o `rol`) se organiza internamente en tres capas:

- **Domain**: entidades, reglas de negocio e interfaces (puertos) del dominio. No depende de detalles técnicos como JPA o Spring.
- **Application**: servicios de aplicación que implementan los casos de uso (puertos IN) y orquestan el comportamiento del dominio.
- **Infrastructure**: detalles técnicos — controllers REST, DTOs, adapters de persistencia, entidades JPA y repositorios Spring Data.

Estos son actualmente los **únicos dos módulos de negocio implementados** en el backend. No se han creado todavía los paquetes correspondientes a Profesionales, Servicios, Horarios, Disponibilidad, Clientes, Citas, Atención, Pagos ni Dashboard.

## Flujo de una petición

1. El cliente realiza una petición HTTP.
2. El `Controller` recibe la petición y valida el request (Jakarta Validation).
3. El `Controller` invoca un Port IN (caso de uso).
4. El servicio de aplicación (`RolService` / `UsuarioService`) ejecuta el caso de uso sobre el dominio.
5. Si necesita persistencia, el servicio utiliza un Port OUT (`RolRepositoryPort` / `UsuarioRepositoryPort`).
6. El adapter de persistencia (`RolPersistenceAdapter` / `UsuarioPersistenceAdapter`) implementa ese contrato.
7. Spring Data JPA accede a PostgreSQL a través de la entidad JPA correspondiente.
8. La respuesta se mapea a un DTO y vuelve al `Controller`.

Los errores de dominio (por ejemplo, rol no encontrado, email duplicado) se centralizan en `shared/web/GlobalExceptionHandler`, que los traduce a respuestas HTTP mediante `ApiError`.

## Configuración inicial de la base de datos (primera vez)

Antes de ejecutar el backend por primera vez en una máquina nueva, la base de datos y las tablas **deben existir ya creadas** — con `spring.jpa.hibernate.ddl-auto=validate`, Hibernate solo verifica que el esquema exista, nunca lo crea. Sin este paso, la aplicación falla al arrancar con `SchemaManagementException: missing table [rol]`.

Desde DataGrip (o `psql`), conectado como superusuario (`postgres`):

```sql
-- 1. Crear el usuario de la aplicación
CREATE USER salonpro_admin WITH PASSWORD 'salonpro123!';

-- 2. Crear la base de datos
CREATE DATABASE salonpro
    WITH
    OWNER = salonpro_admin
    ENCODING = 'UTF8';
```

Ya conectado a la base **`salonpro`** (no a `postgres`), crear las tablas actuales:

```sql
CREATE TABLE rol (
    rol_id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    nombre_rol VARCHAR(255) NOT NULL UNIQUE
);

CREATE TABLE usuario (
    usuario_id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    rol_id BIGINT NOT NULL,
    nombre VARCHAR(80) NOT NULL,
    apellido VARCHAR(80) NOT NULL,
    email VARCHAR(150) NOT NULL UNIQUE,
    password_hash VARCHAR(255) NOT NULL,
    telefono VARCHAR(30),
    activo BOOLEAN NOT NULL,
    fecha_creacion TIMESTAMP NOT NULL,
    CONSTRAINT fk_usuario_rol FOREIGN KEY (rol_id) REFERENCES rol(rol_id)
);
```

Este script deberá ampliarse a medida que se agreguen nuevos módulos (Profesionales, Servicios, etc.).

## Configuración del backend

Archivo: `src/main/resources/application.properties`

Controla, entre otras cosas:

- `server.port`: puerto en el que se levanta el servidor (actualmente `8082`).
- `spring.datasource.url`, `spring.datasource.username`, `spring.datasource.password`: conexión a PostgreSQL.
- `spring.jpa.hibernate.ddl-auto`: estrategia de validación/generación del esquema (actualmente `validate`, es decir, el esquema debe existir previamente en la base de datos).
- `spring.jpa.show-sql`: muestra las sentencias SQL generadas por Hibernate en consola.

> **Nota sobre credenciales:** por simplicidad para trabajar en equipo durante la materia, `application.properties` está versionado con credenciales de desarrollo compartidas (`salonpro_admin` / `salonpro123!`, iguales a las creadas en el paso anterior). Esto es aceptable para un proyecto académico corriendo en local, pero **no debe replicarse este patrón en un entorno real/productivo** — ahí las credenciales deberían salir de variables de entorno o un gestor de secretos, nunca de un archivo versionado.

## Base de datos y documentación de diseño

La implementación actual del backend (entidades JPA en `*/infrastructure/persistence/entity/`) debe considerarse la **referencia principal** para conocer las tablas y relaciones actualmente utilizadas: hoy existen las tablas `usuario` y `rol`.

Los documentos almacenados en `docs/04-model` corresponden a distintas etapas de diseño realizadas durante la materia (modelo conceptual, DER lógico, modelo físico, plan de migración, etc.) y pueden reflejar decisiones anteriores — ya sea porque el código todavía no llegó a implementarlas, o porque el equipo decidió ampliarlas (por ejemplo, los campos de autenticación de `usuario`: `nombre`, `apellido`, `email`, `password_hash`, `telefono`, `activo`, `fecha_creacion`) sin haber actualizado todavía esos documentos.

## Ejecución

1. Tener PostgreSQL activo.
2. Verificar que exista la base de datos y las tablas (ver [Configuración inicial de la base de datos](#configuración-inicial-de-la-base-de-datos-primera-vez)).
3. Revisar `application.properties`.
4. Abrir `salonpro-backend` en IntelliJ.
5. Esperar a que Maven descargue las dependencias.
6. Ejecutar la clase principal `SalonproBackendApplication`.
7. Confirmar en consola que inició correctamente.

O desde terminal, dentro de `salonpro-backend/`:

```bash
./mvnw spring-boot:run
```

## Endpoints disponibles

### Usuarios (`/api/usuarios`)

| Método | Ruta                         | Descripción                          |
|--------|------------------------------|---------------------------------------|
| POST   | `/api/usuarios`              | Crear un usuario                      |
| GET    | `/api/usuarios`               | Listar todos los usuarios             |
| GET    | `/api/usuarios/{id}`         | Buscar un usuario por id              |
| GET    | `/api/usuarios/rol/{rolId}`  | Listar usuarios por rol               |
| PUT    | `/api/usuarios/{id}`         | Actualizar un usuario                 |
| DELETE | `/api/usuarios/{id}`         | Eliminar un usuario                   |

### Roles (`/api/roles`)

| Método | Ruta                | Descripción                  |
|--------|---------------------|-------------------------------|
| POST   | `/api/roles`        | Crear un rol                  |
| GET    | `/api/roles`         | Listar todos los roles        |
| GET    | `/api/roles/{id}`   | Buscar un rol por id          |
| PUT    | `/api/roles/{id}`   | Actualizar un rol             |
| DELETE | `/api/roles/{id}`   | Eliminar un rol               |
